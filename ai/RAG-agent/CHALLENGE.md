# طراحی RAG Agent

**زبان:** Python

---

## معرفی مسئله

یک **RAG Agent** (Retrieval-Augmented Generation) پیاده‌سازی کنید که سوال کاربر را دریافت کند، اسناد مرتبط را جستجو کند و با استفاده از یک مدل زبانی پاسخ مستند تولید کند.

---

## هدف چالش

پیاده‌سازی تابع `rag_agent` در فایل `solution.py` که:

```python
def rag_agent(query: str) -> dict:
    ...
```

- راه‌حل نباید وابسته به محتوای اسناد نمونه یا یک دامنه مشخص باشد. در ارزیابی ممکن است از مجموعه اسناد کاملاً متفاوتی استفاده شود؛ بنابراین پیاده‌سازی باید برای هر نوع سند و هر موضوعی قابل استفاده باشد.

---

## ورودی

```python
query: str  # سوال کاربر به زبان فارسی
```

---

## خروجی پایه

تابع باید یک `dict` با ساختار زیر برگرداند:

```python
{
    "answer": "پاسخ تولیدشده توسط مدل زبانی",
    "documents": [
        {"id": 1, "text": "متن سند اول"},
        {"id": 2, "text": "متن سند دوم"}
    ]
}
```

- فیلد `documents` لیست اسنادی است که در تولید پاسخ استفاده شده‌اند.
- `id` از ۱ شروع می‌شود و `text` از پاسخ سرویس جستجو گرفته می‌شود.
- در صورتی که سرویس جستجو خطا بدهد یا نتیجه‌ای برنگرداند، تابع نباید crash کند.

---

### Citation

پاسخ تولیدی باید شامل ارجاع به اسناد باشد.

در متن `answer` به اسناد ارجاع بدهید و فیلد `citations` هم برگردانید:

```python
{
    "answer": "طبق ماده ۱ قانون مدنی <cite>1</cite> این قرارداد معتبر است.",
    "documents": [{"id": 1, "text": "..."}, {"id": 2, "text": "..."}],
    "citations": [1]   # id اسناد ارجاع‌شده — همان عدد داخل <cite>
}
```

- در متن `answer`، ارجاع‌ها با تگ `<cite>N</cite>` مشخص می‌شوند که `N` شناسه سند (id) است.
- فیلد `citations` لیستی از همان شناسه‌های سند است.
- مقادیر `citations` باید با تگ‌های `<cite>` در متن `answer` مطابقت داشته باشند.

## سرویس جستجو

یک سرویس HTTP برای جستجو در اسناد در دسترس است.

**درخواست:** `GET {SEARCH_API_URL}`

**پارامترها:**

| پارامتر      | نوع    | توضیح       |
| ------------ | ------ | ----------- |
| `query_text` | string | متن جستجو   |
| `top_k`      | int    | تعداد نتایج |

**پاسخ:** لیست مستقیم از اسناد:

```json
[{ "text": "متن سند اول" }, { "text": "متن سند دوم" }]
```

> **نکته:** در محیط تست محلی، سرویس جستجو با یک mock جایگزین شده که از فایل `input_data/documents.json` می‌خواند. کد شما نباید تفاوتی داشته باشد، بنابراین باید سرویس جستجو و درخواست به api جستجو به درستی پیاده سازی شود.

- اسناد موجود در محیط تست صرفا نمونه هستند و نماینده داده‌های واقعی مورد استفاده در ارزیابی نهایی نیستند.

## مدل زبانی

مدل زبانی از طریق API سازگار با OpenAI در دسترس است. کلید API و آدرس سرور از طریق متغیرهای محیطی داده می‌شوند.

---

## متغیرهای محیطی

```bash
LLM_BASE_URL      # آدرس سرور مدل زبانی
LLM_API_KEY       # کلید احراز هویت LLM
LLM_MODEL_NAME    # نام مدل
SEARCH_API_URL    # آدرس سرویس جستجو
SEARCH_API_KEY    # کلید احراز هویت سرویس جستجو
```

مقادیر واقعی `LLM_BASE_URL`، `LLM_API_KEY`، و `LLM_MODEL_NAME` برای دسترسی به مدل زبانی به شما داده شده‌اند.

نیازی به مقداردهی `SEARCH_API_URL` و `SEARCH_API_KEY` از سمت شما نیست. در محیط تست به‌صورت خودکار به سرویس Mock متصل می‌شوند.

**نحوه خواندن صحیح:**

```python
import os
base_url = os.environ["LLM_BASE_URL"]
api_key  = os.environ["LLM_API_KEY"]
```

❌ نوشتن مقدار ثابت در کد مجاز نیست:

```python
# اشتباه
client = OpenAI(api_key="sk-...")

# درست
client = OpenAI(api_key=os.environ["LLM_API_KEY"])
```

## محدودیت‌ها

- کد باید به زبان Python نوشته شود.
- هیچ مقدار ثابتی (API key، URL) نباید مستقیم در کد باشد.
- تابع نباید در صورت خطای سرویس جستجو crash کند.
